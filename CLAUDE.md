# Life Dashboard

Personal life-logging dashboard aggregating external apps (Todoist, Strava, Apple Health, Apple Calendar, Obsidian). Single user (Sienna). External apps stay the source of truth — we pull read-only by default and write back only where the API is good (Todoist: completing tasks). Todoist uses the **unified v1 API** (`api.todoist.com/api/v1`, cursor pagination) — REST v2 returns 410.

## Commands

```bash
pnpm dev            # api (tsx watch, :3001) + web (vite, :5173) in parallel
pnpm db:up          # local docker postgres — offline fallback; also required by db:copy-to-neon (it runs psql/pg_dump inside the container)
pnpm db:generate    # drizzle-kit generate (after schema changes)
pnpm db:migrate     # apply migrations (against whatever DATABASE_URL points at — normally Neon)
pnpm db:copy-to-neon # local -> Neon data migration; --manual-only for just books/exercises (see below)
pnpm typecheck      # all workspaces
pnpm test           # vitest, colocated *.test.ts (only pure logic — see Workflow)
```

Node 24 via nvm (`.nvmrc`). Non-interactive shells may resolve Node 18 — prefix with `source ~/.nvm/nvm.sh` if needed. Env lives in root `.env` (see `.env.example`); the API and drizzle-kit both load it from repo root.

## Two machines (PC + laptop) — shared Neon Postgres

Both machines run the same app against **one shared Neon Postgres** (free tier) — there is no DB syncing, they just point at the same `DATABASE_URL`. The local docker-compose Postgres stays in the repo as an offline fallback (commented-out URL in `.env`).

Neon specifics: database is Neon's default **`neondb`** (not `life`), us-east-2, Postgres **18** (local container is 17 — fine, nothing version-specific in play). Free tier scale-to-zero means the first query after idle takes a few seconds to wake the endpoint — a slow first page load after opening the dashboard is normal, not a bug.

**Migration complete (as of 2026-08-05):** both machines point at Neon. The PC's manual data (53 imported books + real exercises) was copied over with `--manual-only`; Neon now holds the union of both machines' data (books, exercises, period days, todos, calendar, holdings, Plaid transactions).

- **Use Neon's direct (non-pooled) connection string**, not the `-pooler` one. drizzle-kit migrate needs a real session; PgBouncer in transaction mode breaks it.
- **SSL needs no code change** — postgres-js parses `sslmode` off the URL itself (`index.js:443`) and `require`/`allow`/`prefer` set `rejectUnauthorized:false` (`connection.js:283`). `.env.example` uses `verify-full`; drop to `require` if a handshake ever fails.
- **`.env` canonical copy lives in a Bitwarden secure note** — the repo is public, so it is never committed or cloud-synced in plaintext. After changing a var: update the note, then paste it onto the other machine. `.env.example` stays the shared contract; keep it current when adding a var. Known drift: the laptop lacks `FINNHUB_API_KEY` + `ICLOUD_EMAIL`/`ICLOUD_APP_PASSWORD` (present on the PC), so Finance quotes and calendar sync only run from the PC. A connector with missing creds is silently skipped — check which machine synced last (`sync_runs`) before debugging "calendar isn't updating".
- **Migrating data**: `scripts/db-copy-to-neon.mjs` copies local → Neon. Run migrations against Neon first (`DATABASE_URL="$NEON_DATABASE_URL" pnpm db:migrate`), then run it with `DATABASE_URL` still pointing local and `NEON_DATABASE_URL` set. Neither machine has `pg_dump`/`psql` installed — the script runs both **inside the docker `db` container**, so `pnpm db:up` must be running.
  - Default mode copies all four tables via `pg_dump --data-only`, and **requires an empty target** (it replays rows verbatim, so anything already synced collides on `events_source_external_id`).
  - `--manual-only` copies just the `source: "manual"` events — the only data no connector can rebuild. It excludes `id` (target sequence assigns fresh ones) and inserts `on conflict do nothing`, so it is **idempotent and safe against a non-empty Neon**. This is the mode to use once anything has synced.
- **Only `source: "manual"` data is irreplaceable** (books, exercises). Todoist/calendar/holdings all re-sync from their connectors, so when in doubt the machine with the most manual entries is canonical.
- Both machines running `pnpm dev` at once is safe — connector upserts are keyed on `(source, external_id)` so they converge — but it does double up `sync_runs` rows.

## Architecture rules

- **Generic schema only.** All sources normalize into `events` (things with timestamps) and `metrics` (daily scalars) in `packages/db/src/schema.ts`. Do NOT add per-source tables without strong justification.
- **Connector pattern.** Every source: fetch → normalize → upsert on `(source, external_id)` (or `(source, name, date)` for metrics) → record a row in `sync_runs`. Connectors live in `apps/api/src/connectors/`.
- **Every connector records sync_runs** — status `running` → `ok`/`error`. Silent sync failure is the failure mode we guard against.
- **Per-symbol/per-item API failures must degrade, not fail the batch.** A quote/beta/event that can't be fetched becomes `null`/skipped; one bad item must never 500 the whole response (learned via Finnhub 403 on SPAXX).
- **Manual-entry pattern** (exercise, books): rows in `events` with `source: "manual"` and a per-kind `type`; entry fields live in `payload`; `externalId` is a randomUUID. Zod input schemas live in `packages/shared` and are parsed in the route (the global error handler turns ZodError into a 400).
- **All Obsidian vault I/O goes through the `VaultStore` interface** (Phase 4). Never write to the vault path directly from connectors/routes. v1 impl is direct filesystem; it will be swapped for an Obsidian-Git impl when hosting moves off the MacBook.
- **Mac-coupled integrations** (iMessage chat.db, anything AppleScript) live in `bridges/` as standalone scripts that POST to the API — the core app must never assume it runs on macOS.
- **Auth:** every `/api/*` route requires `Authorization: Bearer $API_TOKEN` (hook in `apps/api/src/index.ts`). Webhooks (`/webhooks/*`) use their own shared secrets instead.
- **Thin frontend.** Logic belongs in the API; the web app renders and calls. A future native app should be possible as a second thin client.

## What's built

Sync loop: pull connectors run on API boot, then every 5 min (`runSyncs` in `index.ts`); each configured connector is isolated so one failing doesn't block the others. `POST /api/sync` triggers all of them manually.

### Todos (source `todoist`)
Todoist v1 sync + `POST /api/todos/:externalId/close` write-back. Tasks absent from the active set get `payload.status = "completed"` locally.

### Finance — Stocks (sources `fidelity` + `nm` + `factset` + live quotes)
- **Three accounts, one dashboard**: folder-style tabs at the top of `Stocks.tsx` — **Individual** (Fidelity brokerage, source `fidelity`), **NM** (Northwestern Mutual via Plaid, source `nm`), **FactSet 401k** (source `factset` — same Fidelity Plaid item as Individual, split out by account subtype `401k`; its single holding is a no-ticker target-date fund priced via institution price). `GET /api/finance/portfolio?account=individual|nm|factset` (default individual); everything below the tabs is the same components fed per-account. Tab choice persists in `localStorage("stocks.account")`.
- **CSV upload**: `POST /api/finance/holdings/upload?account=individual|nm|factset` (default individual) takes a positions CSV as raw text body (`text/csv`) and replaces that account's holdings. Parsed with papaparse in `connectors/fidelity.ts` — loose header matching (Symbol/Quantity/Cost Basis/Current Value variants), strips `$`/commas, `SPAXX**` asterisks, skips `Pending Activity` + disclaimer rows. Stored as `events` (`type: "holding"`, `externalId` = symbol); re-upload replaces (symbols missing from the upload are deleted = sold); **on a Plaid-linked account a CSV is only a manual override until the next 5-min sync replaces it**. Every tab's header has the Upload CSV button + that account's Plaid state (Link Plaid button ↔ green "Plaid linked" check). **Optional Plaid path**: link at `/plaid-link?mode=investments&account=individual` → `PLAID_FIDELITY_ACCESS_TOKEN`; once set, the same investments sync (below) writes `source: "fidelity"` every cycle and its first prune deletes the CSV rows (Plaid becomes source of truth; a CSV upload still works as a manual override until the next sync). Status widget's Fidelity row flips CSV/manual → REST API accordingly.
- **Holdings (NM)**: second Plaid item, `investments` product, token in `PLAID_NM_ACCESS_TOKEN` (link at `/plaid-link?mode=investments` — the NM tab shows a CTA to it while `linked:false`). `syncInvestmentHoldings(source)` in `connectors/plaid.ts` (shared by NM + the Fidelity Plaid path) pulls `/investments/holdings/get` every 5-min cycle (no cursor — full replace each run, prune = sold), aggregates per security across sub-accounts, upserts `events` (`type: "holding"`, `externalId` = Plaid `security_id`), skips NM's zero-quantity/zero-value cash ledger artifacts, and nulls cash cost bases (no cost semantics — they once produced a phantom gain and a /~0 gain %). Securities without a real ticker (annuity sub-funds) get a name-derived display symbol and are excluded from Finnhub/Yahoo calls (`quotable` flag + `TICKER_RE` in `finance.ts` — the cash fallback symbol "CASH" collides with Pathward's real NASDAQ ticker); their `institution_price` rides in the payload and is the price fallback — that's what makes a fund-heavy NM account priceable at all.
- **Cash stat**: `totals.cashValue` = value in `isCash` positions (NM `securityType: "cash"`; Fidelity money-market symbols in `FIDELITY_CASH_SYMBOLS` — $1-NAV core positions only, never non-par funds like FEDDX). Cash is par-priced at $1 (`quantity` = dollars; SPAXX's blank CSV Quantity falls back to Current Value), counts in market value but carries no cost/gain. Shown as a 5th tile on the Stocks page only (`Totals showCash`); Home/Finance widgets stay 4-up.
- **Live prices**: `GET /api/finance/portfolio` (in `finance.ts`) prices holdings via Finnhub `/quote` (`FINNHUB_API_KEY`, 45s in-memory cache in `connectors/finnhub.ts`). Free tier can't price money-market/mutual funds (SPAXX, FEDDX → 403 → null, shown as "—" — unless the holding carries an NM `institutionPrice`, which fills price/value but not day change).
- **Per-symbol stats**: one `yahoo-finance2` v4 quoteSummary call per symbol (`connectors/yahoo.ts` → `fetchSymbolStats`, 12h cache, no key needed) supplies beta, sector, dividend yield, and the 52-week range. Sector falls back from `assetProfile.sector` (stocks only) to `fundProfile.categoryName` (ETFs/funds — otherwise an ETF-heavy portfolio is all "Other"); yield prefers the first *positive* of `dividendYield`/`yield`/`trailingAnnualDividendYield` (funds carry a literal 0 in `dividendYield`).
- **Risk**: beta → riskTier per position (thresholds in `finance.ts:betaToTier`) + portfolio rating = value-weighted beta bumped a notch if top position >30% or high-risk value >40%. Deterministic arithmetic, no AI.
- **Dashboard** (`Stocks.tsx`): totals tiles (incl. day $ + %), portfolio-value line chart, positions table (day $, allocation %, yield, 52w range tick, risk badge), sector-allocation bars + risk card, CSV upload at the bottom. Charts follow the Bank.tsx system (hand-rolled SVG, single accent `#3987e5`).
- **Value history**: `buildPortfolio` upserts a daily `metrics` row (`name: "portfolio_value"`, `source` = the account's source — `fidelity` for Individual, `nm` for NM — last write of the day wins) on every priced build — page loads *and* the 5-min sync loop — so each account's series accumulates without visits (Individual live snapshots since 2026-08-07, PC only since it needs `FINNHUB_API_KEY`). Served as `history` in the portfolio response; the chart renders once ≥2 days exist.
- **Backfilling the value series** (`apps/api/scripts/backfill-portfolio-value.ts`, `pnpm backfill:portfolio --from YYYY-MM-DD [--dry-run]`): one-time seed of the gap before live snapshots existed. Values each day as `current quantity × Yahoo daily close` (yahoo-finance2 `chart`), so it's **only exact while share counts are unchanged over the window — `--from` must be the day after the last buy/sell** (used 2026-07-08). Rows get `payload.backfilled = true` and insert `on conflict do nothing`, so it never clobbers a real snapshot and is idempotent. It **restricts to the symbols Finnhub can price** (calls `fetchQuotes` first) to match the live series' composition — otherwise a fund Yahoo can price but Finnhub can't (FEDDX) inflates the historical days and leaves a fake step at the seam. Uses split-adjusted `close` (dividend-inclusive), ET calendar day to align with the live snapshot's local date.
- **Backfilling the 401k** (`apps/api/scripts/backfill-401k.ts`, `pnpm backfill:401k [--dry-run]`, run 2026-08-08 → 371 days from 2025-03-07): the fund has no ticker, so this reconstructs entirely from Plaid `/investments/transactions/get` — units per day walked backwards from the current stored quantity, NAV per day linearly interpolated between per-contribution prices (Fidelity's 401k feed leaves `price` null; `amount/quantity` per tx IS the NAV) anchored at today's institution price. Two Plaid quirks handled: the transactions endpoint can use a **different security_id** than holdings for the same fund (aliased when 1:1), and the null prices. Same idempotent on-conflict-do-nothing writes, source `factset`.

### Finance — Bank (source `plaid`)
- **Sync** (`connectors/plaid.ts`): read-only via Plaid's incremental `/transactions/sync`; cursor persisted in `sync_runs.cursor`. Transactions → `events` (`type: "transaction"`, `externalId` = `transaction_id`); `removed` entries hard-deleted. Each run also refreshes account metadata + live balances via `/accounts/get` → `events` (`type: "account"`, `externalId` = `account_id`). Link tokens request `days_requested: 730` (24-month history) — **only applies at link time**, so more history on an existing item = re-link via `/plaid-link`. A fresh/invalid cursor (first sync or post-re-link INVALID_CURSOR) **wipes all plaid transaction rows and re-pulls** — required because a re-linked item re-issues the full history under new transaction_ids (rows would otherwise duplicate).
- **Linking**: browser handshake on `/plaid-link` (`PlaidLink.tsx`) → paste the printed access token into `PLAID_US_BANK_ACCESS_TOKEN` in `.env`.
- **Dashboard** (`spending.ts` → `GET /api/finance/spending?month=YYYY-MM`, default latest): per-month summary (spend/income/refunds/projected pace), 12-month trend, daily cumulative series, category + per-account + top-merchant breakdowns, and DIY recurring-charge detection (≥3 charges, steady amount ±25%, cadence windows weekly/biweekly/monthly/yearly; `active` = not overdue by >2 cycles).
- **Recurring series** (`recurring_series` table — like `settings`, a documented generic-schema exception): detection output is only the **Suggested** list; confirming/dismissing (`POST /api/recurring`, upsert on normalized merchant key; `DELETE /api/recurring/:id` = restore) stores a durable content pattern (merchant + amount + cadence) — **never transaction ids**, so series survive pending→posted id swaps and the re-link wipe. Confirmed series re-match history each request (merchant key + amount ±25% — amount is what separates the Netflix subscription from a Netflix gift card); the widget's Confirmed section shows live stats + totals (monthly $/count, annual-billed-only $/count, and an all-cadence annualized total — weekly×52/biweekly×26/monthly×12/yearly×1, active series only). Dismissed series are hidden from suggestions but restorable from the widget footer. Each confirmed series has an **expiration** (`expires_on`, null = indefinite — shown as ∞, edited in place via a date input in the Confirmed grid, `PATCH /api/recurring/:id`); a matched charge dated *after* it sets `expired` and a red warning triangle on the row — the "this should have stopped billing" flag. A charge detection can't catch (price change broke the amount match, or <3 charges) is markable from the **transaction grid's right-click context menu** (Types section) — its Recurring toggle confirms a series from that charge's merchant + amount (cadence defaults to monthly; toggling off deletes the matched series). Every served transaction carries `recurringSeriesId` (null = unmatched) to power the toggle + row pill.
- **Tags** (`tags` + `tag_rules` tables, logic in `tags.ts`): user-defined merchant labels — pure data, no per-label logic. Rules key on the normalized merchant key (same `merchantKeyOf` as recurring — content, not transaction ids, so they survive re-links) and apply to every past+future charge from the merchant. Applied from the right-click context menu's **Tags** section — on transaction rows *and* recurring (confirmed/suggested) rows; checking tags the *merchant* (`TagMenuSection` is the shared block). Both grids show a compact **tags column**: one hashtag glyph per tag in the tag's color, full name in the tooltip (`TagMarks`; recurring rows carry `merchantKey` for the lookup). Audited in the **Tags** card at the page bottom: one expandable row per tag (chevron dropdown → the tag's merchants with per-merchant sums), columns for merchant count and the tag's net transaction sum in the **selected month** (client-side over `d.transactions`, so it follows the month switcher; refunds show as green +). The **Tag trend** card (under the trend/daily pair) charts hand-picked tags as grouped (side-by-side) monthly bars in each tag's own color, scaled to the largest single tag-month — the one legitimately multi-hue chart (categorical series with user-assigned hues; legend always shown). Per-tag month sums ride in `trend[].tagSpend` (computed server-side for every tag); the monitored subset starts empty and persists in `localStorage("bank.monitoredTags")` via its funnel dropdown. Net-refund months render as no segment (tooltip stays exact); `TAG_HEX` in `lib/tags.tsx` maps color tokens to hex for SVG fills. Transactions carry `merchantKey`, the dashboard carries `tagged`, and `GET/POST/PATCH/DELETE /api/tags` + `POST /api/tags/:id/toggle` manage them. **Editing tags**: sidebar's "Edit Tags" (hashtag icon, above Settings) opens a **secondary drawer** beside the sidebar on desktop; on mobile it's the `/tags` page (hidden route, back via MobileHeader). Add input + per-tag rename/recolor (8-color palette in `TAG_COLORS`, new tags cycle it)/delete — everything autosaves, no save button. Colors are token names; `lib/tags.tsx` maps them to static Tailwind classes (dynamic class names don't compile). Deleting a tag cascades its rules. Future layers in todo.md: per-transaction overrides (one-off adds, rule exclusions), category rules, tag filters. "Spend" excludes internal transfers/card payments (`NON_SPEND_DETAILED`, keyed on Plaid detailed categories — LOAN_PAYMENTS_OTHER_PAYMENT is US Bank's card-payment label) and is net of refunds. `normalizeMerchant` collapses statement descriptors ("Chidoordash.comca") into brands (DoorDash etc.) for merchant/recurring grouping. `amount > 0` = money out (Plaid convention).
- **Bank page** (`Bank.tsx`): month switcher (also click a trend bar to jump), stat tiles (Spent + vs-prev delta, Income, Net, DoorDash), monthly-trend columns (selected = blue `#3987e5`, rest zinc — emphasis form, single measure = single hue), daily cumulative line with crosshair tooltip, category bars, accounts/merchants lists, the recurring widget (totals tiles + Confirmed/Suggested grids with +/× icon actions), and the month's transactions as a grid (column headers, per-row kebab menu). Grid rows pair responsive `grid-cols-[...]` templates with `hidden sm:block` cells — the two must change at the same breakpoints or columns shift. The row menu is fixed-positioned from the kebab's rect (the list's overflow scroll would clip an absolute dropdown) and closes on outside-pointerdown/scroll. Charts are hand-rolled SVG, no library. Monthly trend + Through the month sit side by side (`lg:grid-cols-2`); those two charts size their viewBox from the container's measured width (`useMeasuredWidth`, 1 unit = 1 CSS px) so axis/label text renders at true pixel size at any card width — a fixed-640 viewBox shrinks text unreadably at half width. Other fixed-viewBox charts (Stocks, Projects) still assume full-width cards.

### Period tracking (source `manual`, type `period`)
`period.ts`: menstrual cycle tracking, one `events` row per marked day (no ranges — a day is either marked or not), toggled via `POST /api/period/toggle`. No dedicated page; surfaces as a toggle inside the Calendar/Exercise day view (`lib/period.tsx` → `usePeriodDays`) for red-circle rendering on the calendar grid.

### Exercise (source `manual`, type `exercise`)
`POST/GET /api/exercises`. Required: `type` (run/gym/yoga/bike/hike/custom) + `date` (YYYY-MM-DD); optional description/totalTime(min)/caloriesBurned. `startTs` = noon UTC of the date (keeps the calendar day TZ-stable). List sorted by workout date desc.

### Reading (source `manual`, type `book`)
`POST/GET /api/books` + `PUT /api/books/:id` (**full-replace** edit — the form resubmits every field; omitted optionals clear). Required: title + status (reading/complete/queued/abandoned); rating is 0.5–5 in half-star steps (Zod `multipleOf(0.5)`); dates optional. List sorted: no-completion-date books first (current read on top), then `dateCompleted` desc. History note: 53 books were imported from `OneDrive/Documents/life-dashboard.xlsx`; synthetic completion dates fall on the **1st of a month** = "real date unknown", non-1st dates are real.

### Calendar (source `calendar`)
- **iCloud CalDAV** read-only in `connectors/icloud.ts` (tsdav + node-ical, Basic auth with `ICLOUD_EMAIL` + `ICLOUD_APP_PASSWORD` app-specific password). Never use public ICS links — Sienna's events contain locations. Syncs a −90d/+365d window: RRULE expansion, EXDATE, per-instance overrides; recurring instances get `externalId` = `uid:occurrenceISO`; events gone from the window are pruned. `GET /api/calendar/events` serves them start-ordered.
- **Per-day cashflow** (`spending.ts` → `buildDailyCashflow` → `GET /api/finance/cashflow`): net = income − spend per day, reusing the Bank page's `isSpend`/`isRefund`/`isIncome` classification (tx loading factored into `loadTxs`/`toTx`, shared with the dashboard). Returns only days with movement. Surfaces on the calendar grid as a small chip beside the day number (right of weather): `-$55` red for money out, `+$X` green for money in (paydays show the whole deposit — it's net *cashflow*, not spend-only), grey `$0` for a covered day with no movement; hover shows the spend/income split. Rendered by `CashflowBadge` in `Calendar.tsx`, in all three cell layouts (month cell, expanded day, week-scan header). "Covered" = first transaction date → today (`isCashCovered`); outside that window (pre-history or future) the chip is omitted, not shown as a misleading $0. Each day also carries its confirmed-recurring portion; the filter dropdown's **Cashflow → Recurring** toggle (off by default — the calendar is for discretionary spend) adds/removes it from the chips client-side, no refetch (tooltip notes the excluded amount); **Cashflow → Tags** excludes tagged merchants' transactions from the sums (server-side `?excludeTags`, so multi-tag merchants aren't double-subtracted). All the filter dropdown's choices persist in `localStorage("calendar.filters")` — no save button, written on every toggle.
- **Calendar page** (`pages/Calendar.tsx`): hand-rolled Monday-start 6×7 grid (no library, on purpose). Fixed 54rem height; week rows are flex items (`basis-0`), expansion works by animating `flex-grow` (expanded week `grow-[25]` = 45rem, others compress to ~1.8rem). Inside an expanded week, a clicked day widens the same way horizontally (siblings squeeze to `basis-9`). Hover tabs on each row edge toggle week expansion; clicking any day from anywhere expands its week + day. Blue outline marks the current selection (week or day). Chips: violet = iCloud events (`9:30 AM Title`), blue = exercises (`30min gym`); overflow clips — expand the day to see everything. A "Last saved …" stamp in the controls row shows the most recent day-log edit (`GET /api/calendar/last-updated` → `getLastUpdated`, max `calendar_days.updatedAt`), refreshed via the `["calendar-last-updated"]` query which the log's save invalidates.
- **Expanded-day detail** (`DayForm` → left column: `DayLog`, `TodosForDay`, `TransactionsForDay`, `CommitsForDay`; right column: `DaySchedule`). The left column scrolls as a whole once sections outgrow the fixed calendar height; each list also caps at `max-h-56` and scrolls internally. Commits share the `["github-commits"]` query with Projects (rows link out to GitHub); days with commits get an emerald code-brackets datalet mark, gated by the filter's **Datalet → Commits** toggle. Days with a non-blank log get an amber pencil mark (**Datalet → Logged**; `GET /api/calendar/logged-days`, whitespace-only logs don't count; the log's autosave invalidates `["logged-days"]` so the mark appears on first write). The log (`DayLog.tsx`) has **no save button — it autosaves on blur** (only when dirty); text is greyed (`text-zinc-400`) while locked and turns white on focus (`focus:text-zinc-100`) to signal edit mode. Todos (due + completed, from the shared `["todos"]` query) and Transactions (`GET /api/finance/transactions/:date` → `buildDayTransactions`, all plaid rows on that day, money-in green with `+`) are read-only lists.
- **Schedule** (`ScheduleTimeline.tsx`): the single 24h-timeline component shared by **both** the expanded-day view (`DaySchedule`, 1 column) and the expanded-week scan (`WeekSchedule`, 7 columns) — both are thin wrappers passing a `dates` array + `gutter`, so the two can't show different schedules. Renders iCloud events (violet) and manual exercises (blue). A block needs a positionable range: calendar `timed` events, and exercises with **both** `time` (HH:MM) and `totalTime` (minutes). Anything without that — all-day events, and exercises missing a time or duration — pins to each column's sticky top (same violet/blue split) so it stays visible while the timeline scrolls. `dense` (multi-column) shrinks type/borders. Because events + exercises now both live in the schedule, the expanded-day header shows **no chips** (only the collapsed month cell still uses `DayChips`).

### GitHub (source `github`)
- **Connector** (`connectors/github.ts`), all GraphQL with `GITHUB_TOKEN` (classic PAT, `read:user` only), trailing-365d window each sync: (1) `viewer.contributionsCollection` calendar (the exact per-day data the profile graph uses — commits/PRs/issues/reviews) → `metrics` (`name: "contributions"`, one row per day, zeros stored so "synced, nothing that day" ≠ missing); (2) `commitContributionsByRepository` → `events` (`type: "repo"`, replace semantics) for per-repo year counts; (3) per-repo default-branch `history(author: viewer)` → `events` (`type: "commit"`, `externalId` = sha, message/url in title/payload), per-repo failures degrade. **read:user sees counts for everything but repo/commit detail only for public repos** — private repos count in the calendar but never appear in repos/commits (upgrade path: fine-grained PAT with read-only Contents). Feature-branch commits join the detail list on merge. Endpoints: `/api/github/contributions`, `/repos`, `/commits`.
- **Heatmap** (`components/Heatmap.tsx`): **generic** GitHub-style year grid — takes any `{date, value}[]` plus a tooltip formatter, so future series (exercise, todos, day logs) reuse it unchanged. Monday-start rows (matches the app's calendars, not GitHub's Sunday), sequential 4-step ramp of the chart accent (dark→bright on the dark surface), month/weekday gutter labels, hover tooltip with exact count, Less→More legend. Optional `selectedDate`/`onSelectDay` props add day selection (ink outline on the picked cell); omit both for a passive widget. `GithubWidget` on Home is the passive consumer.
- **Projects page** (`pages/Projects.tsx`): selectable heatmap (click a day → that day's commits with GitHub links, grouped client-side by local calendar day from `ts`), plus commits-per-repo bars (single measure = single accent, SectorBars form). Day panel's empty state explains the count/detail gap (PRs/reviews/private repos).

### WakaTime (source `wakatime`)

### Settings (`/settings`, table `settings`)
- **`settings` table**: key/value jsonb — a deliberate, documented exception to the generic-schema rule (preferences have no event/metric semantics). UI prefs live under key `"ui"` as `{font, theme, spacing, lineHeight}` (`uiSettingsSchema` in shared; zod defaults make a missing/stale row safe — removed keys like the old `density` enum are stripped on parse, new fields fill from defaults); `GET/PUT /api/settings/ui` → `apps/api/src/settings.ts`. Density is two **sliders**: `spacing` = Tailwind v4's `--spacing` base in rem (0.18–0.3, default 0.225 ≈ 90% of stock — every spacing utility and numeric w-/h- derives from it) and `lineHeight` = the leading ratio for xs/sm text (1.0–1.6, default 1.25; base text gets +0.1; terminal ≈ 1.15). Line-height, not spacing, is what makes list rows feel tall — Tailwind utilities emit `line-height: var(--text-sm--line-height)`, and `applyUiSettings` writes the four vars as **inline styles on `<html>`** (outranking the `@theme` first-paint defaults in index.css), so it all works without touching components.
- **Page**: gear entry pinned to the sidebar bottom (`bottom: true` in `nav.ts`); `pages/Settings.tsx` has a panel registry (only "Style" so far — font + theme dropdowns). Dropdown changes **preview live** (`applyUiSettings` on change); Save persists; leaving the panel without saving reverts to the stored settings (unmount cleanup applies the last stored value via a ref).
- **Apply mechanism**: `lib/settings.tsx` stamps `data-font`/`data-theme` on `<html>` (`ApplyUiSettings` mounted in App.tsx does it on load; save does it directly). `index.css` maps `data-font` to a `--app-font` stack — Inter Variable + JetBrains Mono Variable are bundled `@fontsource-variable` packages imported in main.tsx (no CDN), system/Georgia are plain stacks.
- **Themes without a component rewrite**: components are written entirely in dark zinc utilities; Tailwind v4 utilities resolve through `var(--color-*)`, so a `:root[data-theme="..."]` block in index.css remaps the zinc scale and the whole app flips. **Light** inverts the scale and darkens the **accent text steps** (violet/blue/emerald/sky/amber/red 100–400, used as chip/badge text on tinted washes) to their 600–900 counterparts — washes and solid buttons stay untouched. **Royal Velvet** (ported from the Obsidian community theme, caro401/royal-velvet) retints the same scale to its blue-charcoal darks (#14141b/#1d1e26, text #f8f8f2) and hue-shifts the same accent text steps to its neons (violet→purple, sky→cyan, emerald→green, amber→orange, blue→periwinkle, red→soft red). **Sandbox** remaps only `--color-zinc-950` to near-black (#040405) — cards/nav keep stock zinc-900 and float on the darker page plane. Adding a theme = new value in `UI_THEMES` (shared) + `THEME_LABELS` entry (Settings.tsx, TS-enforced) + an index.css block. Known limitation: hard-coded hex in the SVG charts (Bank/Stocks accents, gridlines, chart text) stays dark-blue-tuned in every non-default theme.

## Gotchas (hard-won, do not rediscover)

- **Non-ASCII in API string literals gets mangled** by tsx/esbuild on this Windows machine (em dash → `â€"` mojibake in responses). Keep runtime strings in `apps/api` ASCII-only; comments are fine (stripped at compile).
- **Tailwind v4 + running vite dev server**: utility classes in a **newly created** file aren't picked up until the dev server restarts (page renders unstyled). Edits to existing files hot-reload fine.
- **DB-mutating buttons get `cursor-pointer`** (+ `disabled:cursor-not-allowed` where they have a disabled state). Tailwind v4's preflight dropped the default `cursor: pointer` on `<button>`, so any control that writes to the DB — completing/clearing/deleting todos, add/edit exercise or book, toggling a period day, uploading holdings — must set it explicitly. Shared controls already do it in one place (`CompleteButton` in `lib/todos.tsx`), so those propagate everywhere. Non-mutating buttons (nav, expand/collapse, Cancel) intentionally keep the default cursor. (The day-log has no button — it autosaves on blur.)
- **Calendar grid flexbox**: every nested flex container needs `min-w-0`/`min-h-0` — the default `min-size: auto` lets chip content blow rows out to 1600px+ wide / uneven heights. If the grid ever looks "randomly oversized", check for a flex child missing its min-size reset.
- **node-ical types**: `VEvent` includes a `Record<string, unknown>` index signature, so `Omit<VEvent, ...>` degrades all fields to `unknown` (cast instead); text fields are `string | { params, val }` — unwrap before use.
- **yahoo-finance2 v4** is class-based: `new YahooFinance({...})`; the static default-export methods are deprecated stubs that return `never` / throw.
- Port 3001 conflicts: a stale API process (hers or a background one) causes `EADDRINUSE` and the *new* process dies while the old one serves stale code — kill the listener on :3001 before debugging "my change isn't taking effect".
- **`.env` edits need a full `pnpm dev` restart, and the two halves drift differently**: Vite auto-restarts on `.env` changes (web gets new values immediately) but `tsx watch` only restarts on *source* changes (API keeps old values). So editing `API_TOKEN` while dev is running = instant 401 on every page, because the web is sending the new token to an API still holding the old one. Same mechanism: changing `DATABASE_URL` leaves the API writing to the old database until restarted — and it cuts the other way too: if `.env` on disk drifts back to the local docker URL (e.g. from pasting an older snapshot while merging in machine-specific keys) while a Neon-connected `tsx watch` is still running, everything *looks* fine until the next source save silently reconnects it to the near-empty local DB. Diff `.env` against `.env.example`/Bitwarden after any manual paste, not just after intentional edits.
- **`tsx -e` compiles to CJS** — no top-level await in one-liners; wrap in an async IIFE. And `import 'dotenv/config'` resolves `.env` from *cwd*, so under `pnpm --filter @life/api exec` it finds nothing (silently falls back to OS-user Postgres auth) — pass env vars explicitly for ad-hoc scripts.
